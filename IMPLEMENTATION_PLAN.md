# План реализации и исправлений

## 1. Текущее состояние

Проект собирает отзывы с двух источников:

- СберЗдоровье / DocDoc;
- ПроДокторов.

Для проверки доступа к DocDoc добавлен скрипт `check_access.py`. Он использует `curl_cffi` с TLS-имитацией Chrome и проверяет не только статус `HTTP 200`, но и наличие реальных отзывов в `__NEXT_DATA__`.

Проверка страницы:

```text
HTTP 200
OK: получены реальные отзывы: 17
```

Это подтверждает, что `curl_cffi` действительно получает страницу врача, а не CAPTCHA-заглушку.

## 2. Выполненные исправления

### 2.1. Удаление браузерного fallback

Удалены Camoufox, Patchright и браузерный fallback.

Причина: для текущей схемы сбора данных браузер больше не требуется, а `curl_cffi` успешно получает страницу и отзывы DocDoc.

Результат:

- приложение не запускает браузер при блокировке HTTP-запроса;
- при CAPTCHA или блокировке источник возвращает ошибку `source_blocked`;
- Dockerfile больше не устанавливает Chromium, Patchright и Xvfb;
- из зависимостей удалены браузерные пакеты.

### 2.2. Исправление циклического импорта

Пакет `collectors` больше не импортирует все модули автоматически через `collectors/__init__.py`.

Причина ошибки:

```text
app.security
  -> collectors.base
  -> collectors.__init__
  -> collectors.http_client
  -> app.security
```

`collectors/__init__.py` теперь является только маркером пакета, а модули импортируются явно.

Проверка:

```text
imports ok
26 passed
```

### 2.3. Проверка и разбор структуры отзывов

Коллектор СберЗдоровья поддерживает актуальную структуру:

```text
preloadedState.doctorReviews.reviewsForSeo
preloadedState.doctorReviews.reviews
```

Также сохранена совместимость со старой структурой:

```text
preloadedState.doctorPage.doctor.reviewsForSeo
```

Для дополнительных отзывов используется endpoint:

```text
https://docdoc.ru/doctors/moreReviews
```

с параметрами:

```text
isHiddenDoctor=0
offset=<количество уже загруженных отзывов>
doctorId=<ID врача>
reviewsSort=new
```

## 3. Этап перевода HTTP-запросов — выполнен

`HTTPClient` переведён на `curl_cffi` с `impersonate="chrome"` для DocDoc/SberHealth и ПроДокторов. Сессия переиспользуется между HTML-запросом и `moreReviews`, поэтому cookies сохраняются.

`httpx` оставлен как транспорт для прочих разрешённых доменов и поддерживается для совместимости с тестовыми клиентами.

Важно сохранить текущие ограничения безопасности:

- проверку разрешённых доменов;
- проверку публичного DNS перед запросом;
- запрет небезопасных редиректов;
- лимит размера ответа;
- ограничение количества редиректов;
- повторные попытки при сетевых ошибках;
- распознавание CAPTCHA и blocking page.

Для ПроДокторов можно оставить текущий `httpx`, если он продолжает работать стабильно. Если защита источника также будет блокировать `httpx`, переключить и этот источник на `curl_cffi`.

## 4. Выполненная реализация и проверки

### Шаг 1. HTTP-клиент — выполнен

- `HTTPClient` поддерживает `curl_cffi` и запускает синхронный запрос через `asyncio.to_thread`.
- Для всех доменов источников используется `impersonate="chrome"`.
- Передаются `Accept`, `Accept-Language`, `Referer`, а для `moreReviews` также `Sec-Fetch-*`, `Origin` и `X-Experiments`.
- Ответ адаптируется к интерфейсу коллекторов: `status_code`, `content`, `headers`, `is_redirect`, `text`, `json()`.
- Ограничение размера применяется во время загрузки, до накопления полного тела.
- HTML разбирается через `response.text`, поэтому кириллица не искажается.

### Шаг 2. Безопасность — выполнен

Сохранены и покрыты тестами:

- allowlist доменов и запрет userinfo/нестандартных портов;
- публичный DNS перед каждым переходом;
- запрет внешних, небезопасных и HTTPS-downgrade редиректов;
- лимит ответа и лимит редиректов;
- повторные попытки сетевых timeout/connection ошибок;
- контролируемые `source_blocked` для HTTP 403/429/503, CAPTCHA и Servicepipe challenge;
- ложные совпадения `captcha` внутри script/style не блокируют обычный HTML.

Небезопасные проверки DNS не отключались.

### Шаг 2. Сохранить безопасность запросов

Перед фактическим запросом продолжать выполнять:

```text
проверка разрешённого домена
проверка DNS и публичности IP
проверка редиректа
проверка размера ответа
проверка CAPTCHA/блокировки
```

Нельзя отключать `validate_public_dns` ради обхода блокировки.

### Шаг 3. Тесты — выполнено

Добавлены тесты для успешного `curl_cffi`, `__NEXT_DATA__`, CAPTCHA/Servicepipe, HTTP 403/429/503, лимита ответа, редиректов, DNS, retry, cookies и передачи ответа коллекторам.

Команда:

```text

```

Результат:

```text

```

### Шаг 4. Ручная проверка — выполнено

`python check_access.py` получил HTTP 200 и 17 реальных отзывов DocDoc.

Локальный API через `python main.py`:

```text
/health -> HTTP 200
/api/v1/getReviews DocDoc all_reviews=false -> HTTP 200, 17 отзывов
/api/v1/getReviews DocDoc all_reviews=true -> HTTP 200, 17 отзывов
```

Проверка `moreReviews` с `offset=10` получила 7 оставшихся отзывов. Кириллица в title и тексте отзывов сохранена.

ПроДокторов через `curl_cffi` отдаёт Servicepipe challenge. Fallback Patchright запускает видимый Chromium под Xvfb и получает HTTP 200, title и 3 отзыва на проверенной странице. Headless Chromium без виртуального дисплея блокируется.

Команды выполнены:

```text

```

Результат: образ собран, контейнер healthy, `/health` возвращает HTTP 200. В контейнере отсутствуют модули Camoufox/Patchright/Playwright и бинарники Chromium/Xvfb.

Контейнерный API DocDoc возвращает HTTP 200 и 17 отзывов. ПроДокторов возвращает контролируемый `503 source_blocked` из-за challenge источника.

## 5. Диагностика блокировки

Если `check_access.py` выводит `HTTP 200` и реальные тексты отзывов, но API приложения возвращает `source_blocked`, первым делом проверять:

1. Каким клиентом выполнен запрос страницы.
2. Передаётся ли `impersonate="chrome"`.
3. Не отличается ли `User-Agent` от TLS-профиля.
4. Не теряются ли cookies между HTML-запросом и запросом дополнительных отзывов.
5. Не срабатывает ли проверка `is_blocked_content` на обычное слово `captcha` внутри JavaScript страницы.

## 6. Ограничения

`curl_cffi` не гарантирует обход всех видов защиты.

Он не решает блокировки, связанные с:

- репутацией IP-адреса;
- датацентровым диапазоном адресов;
- обязательной интерактивной CAPTCHA;
- rate limit;
- поведенческими признаками браузера.

В таких случаях нужно использовать официальный API, разрешённый прокси или согласовать доступ с владельцем источника. Не следует добавлять агрессивные обходы CAPTCHA или массовую ротацию IP.

## 7. Единый Camoufox fallback — выполнено

- Patchright удалён из runtime и Docker.
- Добавлен единый ленивый Camoufox для DocDoc и ПроДокторов.
- `curl_cffi` остаётся первым транспортом; Camoufox запускается только после challenge/отсутствия данных.
- Общий persistent context переиспользуется, параллельные browser-запросы сериализуются.
- Сохранены DNS/allowlist/redirect/size checks, закрытие страниц при ошибках и завершение browser context при shutdown.
- Для `moreReviews` используется та же browser page и cookies.
- В Docker Camoufox запускается через Xvfb без физического экрана.
- Исправлена ошибка Windows: Camoufox больше не закрывает восстановленную стартовую страницу перед `new_page()`.

Проверки:

```text
pytest -q -> 110 passed
Локальный Camoufox -> DocDoc и ПроДокторов: отзывы получены
compileall -> успешно
```

Ранее наблюдавшийся `BrowserContext.new_page: TargetClosedError` был вызван закрытием автоматически созданной `about:blank` страницы. После исправления direct-проверка возвращает отзывы с обоих источников.
